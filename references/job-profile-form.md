# 岗位画像点选表单（job-profile-form.md）

岗位画像采集的**默认交互方式**：`interaction_ask` 点选（选项按钮）。点选保证快、结构化、可复用；自由文本是逃生舱，用于补点选覆盖不到的要求。本文件给出每一轮的题目、选项与调用参数；Agent 按此构造 `interaction_ask` 调用。

## 交互原则（v3：JD 优先，点选兜底）

1. 点选为默认：每问题 2-4 个 display_option；多选用 `multi_select=true`；单选用 `multi_select=false`。**每题允许用户用一句自由文本代替或补充点选**（如「其实是硬件研发」「必须能常驻海外」），写入 `profile_notes`，自由文本优先于点选值。
2. **交互总次数 ≤ 3 次弹窗**，每次弹窗最多 4 题，一次弹窗内连续作答多题；禁止拆成 4 次以上。走 JD 快速通道时只发 1 次确认弹窗。
3. 每次弹窗开头提示：「第 N/3 次弹窗，共 N 题；直接回复"跳过"可跳过本题，未选维度按通用/默认处理。」
4. 用户已有 JD → 走「JD 快速通道」（见下节），不再逐题点选；已根据 JD 预填的项写进各题 display_message（如「已根据 JD 推荐：业务增长类，可改选」），用户只点确认/改选。
5. 所有选项的 description 都要写出「选择影响」（这个选择会把分析引向哪里）。
6. **HR 前置信息补充**（第 3 次弹窗第 4 题）：HR 面试前通过电话/微信已掌握的人选信息，用自由文本题一次收集，并入画像备注，显著提升问题定制精准度（见下）。
7. **英文场景**：弹窗语言跟随**操作者**（中文 HR 用中文弹窗），选项的英文标签见 `en-localization.md` 附录 A；仅操作者为英文使用者时才整场用英文标签。产物语言另按 `en-localization.md` 第二节判定。

## JD 快速通道（优先路径，1 次确认弹窗）

**不新增弹窗入口**——在弹窗 1 之前用一句话问（纯文本消息，不计入 3 次弹窗）：
> 「有具体 JD 吗？粘贴过来我直接抽画像，只留 1 次确认弹窗；没有就走 3 次点选。」

用户已粘贴 JD、或简历里带了岗位描述时，跳过这句话直接进入流程。

### 抽取产出（三级结构，缺一不可）

| 层 | 内容 | 去向 |
|---|---|---|
| **结构化维度** | 能映射到弹窗 1-3 既有键值的项（direction/level/years/education/duty_focus/key_ability/industry_req/...） | 画像键值对，**必须映射，不允许跳过** |
| **JD 特有要求** | 映射不到既有键的原句（如「熟悉 FDA 510(k) 注册流程」「有跨境并购经验」） | `jd_specifics[]`，进入匹配度补充行 |
| **成功要素 2-3 条** | 见下节「成功要素提炼」 | `success_factors[]`，题源第一源 |

原始 JD 全文存 `jd_raw`，**只作提炼依据，不直接进问题设计**。

### 确认弹窗（1 次，**必须包含 JD 覆盖不到的题**）

JD 通道只省掉"能从 JD 读出来的题"，不是省掉必须由人选定的题。弹窗分两类：

**必答（JD 无法提供，不可跳过、不设默认值）**
- `hr_mode`：HR 面按结构化模板还是自由题组——这是内容形态选择，只能人来定

**未答按默认处理并在产物注明**
- `company_stage`：JD 常不写公司阶段 → 默认「成熟稳定期」
- `soft_priority`：只能从 JD 措辞推断（「良好的沟通能力」→ 沟通协作）→ 标注「推断」，不当作确认信息

其余按题分组展示抽取结果（推荐值高亮，可改选）；映射不到的 `jd_specifics` 以文本列出，供用户增删。用户追加的口头要求（「最好是同行业」「要能出差」）→ `profile_notes`，同样参与后续分析。

**冲突优先级（冲突时必须按此裁决，不可含糊）**：用户改选 ＞ `profile_notes` ＞ JD 抽取 ＞ 默认值。冲突项在产物中不隐藏，以补充维度呈现。

### 抽取清洗（硬约束）

- **剥离组织信息**：JD 中的公司名、品牌名、内部项目代号一律不写入 `jd_raw` 之外的任何字段；`jd_specifics` 只留能力要求，不留"某公司某系统"这类内部黑话
- **超长 JD**：只抽取岗位职责与任职要求段落，公司介绍、福利待遇、融资新闻不进入提炼
- **超短 JD**：见下节兜底

### 用户选不出方向时

弹窗 1 第 1 题（job_direction）若用户回复选项外的岗位名称或直接贴 JD，**当场转 JD 快速通道**，不要求用户先归类。点选项只是加速器，不是准入条件。

## 成功要素提炼（有 JD 必做，无 JD 也做）

不论画像来自 JD 还是点选，进入分析前先输出 **2-3 条**成功要素：**「在这个岗位上做好的人长什么样」**。

- 格式：**行为 + 可观察的产出**。例：「能独立把一条产品线从 0 带到有稳定续费，而不是只会拉新」
- 禁止：形容词堆砌（「沟通能力强」「有责任心」）、复述 JD 原句（「负责 XX 工作」）、面试中无法验证的表述
- **数量随信息量走，不凑数**：JD 只能支撑 2 条就写 2 条——与"为配额出题视为违规"同理，为凑第 3 条编一条空话属于违规
- **信息不足的兜底（按顺序执行）**：
  1. JD 模板化、抽不出可观察要素 → 用该职能的通用成功要素补位，并标注「通用模板，建议面试官替换」
  2. 仍不足 → 在确认弹窗里用一句话问：「这个岗位上做得最好的人，和一般人最大的差别是什么？」用户一句话回答通常比 JD 更有信息量
  3. 用户也答不出 → 保留 2 条，产物标注「成功要素信息不足，问题针对性可能下降」
- 用途：题源三源制第一源（高光/能力深挖）的锚点；同时作为匹配度分维对照的补充行
- 若某条要素在 JD 中找不到依据、只能推断 → 标注「推断项」，改用情境题验证，不假设候选人做过

**为什么先提炼再出题**：JD 是筛选器，不是问题模板。照 JD 出题只会得到「请讲讲你怎么做用户增长」这类泛题；先提炼成功要素，才问得出「续费率从 X 到 Y 那一段，你具体动了哪几个杠杆」。

## 弹窗 1：岗位基础画像（4 题，全部单选）

**question_id: job_direction | header: 职能方向 | 单选**
display_message: 「这个岗位属于哪类职能方向？」
- business_growth / 业务增长类 / 销售、市场、商务、增长等面向客户与收入的职能
- product_tech / 产品技术类 / 产品、设计、研发、测试等交付型职能
- ops_delivery / 运营交付类 / 运营、客服、供应链、实施等日常运营职能
- staff_support / 职能支持类 / HR、财务、法务、行政等支持型职能

**question_id: job_level | header: 职级层级 | 单选**
display_message: 「这个岗位的职级层级是？」（选"管理岗"会触发管理幅度追问）
- execution / 执行层 / 专员、初级，按指令交付
- core / 骨干层 / 高级、资深，独立扛事
- expert / 专家层 / 专家、资深专家，输出方法论
- manager / 管理岗 / 带团队、Leader、总监

**question_id: exp_years | header: 经验年限 | 单选**
display_message: 「要求多长相关经验？」
- y1_3 / 1-3 年 / 成长期人选
- y3_5 / 3-5 年 / 能独立负责模块
- y5_8 / 5-8 年 / 项目级负责人
- y8_plus / 8 年以上 / 资深或管理后备

**question_id: education | header: 学历门槛 | 单选**
display_message: 「学历要求到哪一档？」（决定身份诚信段验证严格度，是否查学信网）
- any / 不限 / 大专及以上即可
- bachelor / 本科 / 统招本科优先
- master / 硕士及以上 / 研究生学历要求
- elite / 名校优先 / 985/211 或海外名校

## 弹窗 2：能力与要求画像（4 题）

**question_id: duty_focus | header: 核心职责 | 多选（选 2-3 项）**
display_message: 「岗位最核心的职责重点是哪几项？」（决定业务面问题权重分配）
- result / 结果指标交付 / 业绩、产出可量化，扛指标
- depth / 专业深度输出 / 方案、技术、作品等专业产出
- influence / 跨部门协作与影响力 / 拉资源、推项目、影响他人
- team / 团队建设与管理 / 带人、定目标、培养梯队

**question_id: key_ability | header: 关键能力 | 多选（选 2-3 项）**
display_message: 「必备的关键能力是哪几项？」（逐项对照简历生成匹配度依据）
- industry / 行业经验匹配 / 有同行业或强相关行业背景
- hard_skill / 硬技能达标 / 工具、技术、专业方法达标
- data / 数据分析能力 / 用数据做判断与复盘
- comm / 沟通表达与影响力 / 表达清晰、能影响他人

**question_id: industry_req | header: 行业要求 | 单选**
display_message: 「对行业背景的要求是？」
- any / 不限行业 / 无行业限制
- same / 同行业优先 / 同行业是偏好而非硬性
- related / 强相关行业 / 相邻赛道可接受
- specific / 特定赛道必须 / 硬性要求

**第 4 题自适应（按弹窗 1 的 job_direction 选择其中一题）：**
- job_direction=business_growth → **question_id: sales_kpi | header: 考核方式 | 单选**
  display_message: 「业务增长类岗位的考核方式主要是？」（决定销售/增长题组形态）
  - target / 目标达成 / 以任务完成率考核
  - process / 过程量驱动 / 以过程动作量考核
  - profit / 利润毛利 / 以利润结果考核
  - balanced / 综合平衡 / 多指标综合
- 其他职能方向 → **question_id: work_mode | header: 工作形态 | 单选**
  display_message: 「这个岗位的协作与工作形态是？」
  - solo / 独立执行型 / 按指令独立交付
  - project / 项目协作型 / 跨团队推进项目
  - coord / 资源协调型 / 推动他人或外部资源
  - manage / 管理与授权型 / 带团队并做决策
- 若 job_level=manager（管理岗）→ 以 **question_id: manage_span | header: 管理幅度 | 单选** 替代 work_mode
  display_message: 「管理岗的管理幅度是？」（决定业务面团队管理题组深度）
  - m5 / ≤5 人 / 小团队
  - m10 / 5-10 人 / 中型团队
  - m20 / 10-20 人 / 大型团队
  - m20plus / 20 人以上 / 多层级管理

## 弹窗 3：偏好校准 + HR面模式 + HR 前置信息补充（4 题）

**question_id: company_stage | header: 公司阶段 | 单选**
display_message: 「公司/团队当前处于什么阶段？」（校准稳定性判断与风险容忍度）
- startup / 初创期 / 0-1 打样，重冲劲
- growth / 快速成长期 / 放量扩张，重执行力
- mature / 成熟稳定期 / 体系化运营，重专业度
- transform / 转型变革期 / 第二曲线或组织调整，重适应力

**question_id: soft_priority | header: 软素质 | 多选（选 2-3 项）**
display_message: 「最看重的软素质是哪几项？」（进入待考察点"必查项"）
- drive / 自驱与抗压 / 主动扛事、抗压稳定
- learn / 学习与适应 / 快速上手、拥抱变化
- collab / 沟通与协作 / 团队配合、冲突处理
- logic / 逻辑与条理 / 思考结构化、表达清晰

**question_id: hr_mode | header: HR面模式 | 单选**
display_message: 「HR面问题按哪种方式生成？」
- template / 结构化模板 / 四段固化清单：身份诚信、薪资流水、岗位匹配、动机风险，围绕简历定制
- free / AI 自由发挥 / 6-8 题，每题附考察要点与设计理由

**question_id: hr_insight | header: 前置信息 | 自由文本（无 display_option）**
display_message: 「补充 HR 前期沟通已掌握的人选信息（可选，越全越准）：如薪资期望、到岗时间、离职原因、稳定性信号、背调结果、电话沟通印象等。没有可答"无"。这些信息会并入画像，用于定制面试问题。婚育等隐私信息勿写入问项，仅可作内部背景参考。」

## 常用岗位保存（出口操作，非弹窗）

- 用户未主动要求保存 → 交付清单时在回复末尾问一句「需要把该岗位保存为常用岗位吗？一句话即可」，用户确认后写入用户数据目录的 `common_jobs.json`。
- 用户主动说「保存这个岗位」→ 按当前画像写入；说「覆盖」→ 按岗位名覆盖。
- 用户要求用已保存岗位 → 读用户数据目录 `common_jobs.json`，列出 jobs[].name 供点选（1 次弹窗），选后把对应 profile+jd 直接作为画像输入，跳过其余弹窗。

## 常用岗位库读写（common_jobs.json，存于用户数据目录，不随 Skill 分发）

**文件位置：用户数据目录 `<用户工作区>/.interviewer-kit/common_jobs.json`**（不写在 skill 目录内——skill 升级或分享时个人岗位库不得被带走）。首次使用若不存在，从 skill 内置 `data/common_jobs.json`（空模板 `{"jobs":[]}`）复制创建。结构：
```json
{"jobs":[{"id":"job_xxx","name":"岗位名","jd":"JD原文（可为空）","profile":{"弹窗1-3点选结果":"键值对，另含 profile_notes 自由文本补充、jd_specifics JD 特有要求"},"success_factors":["成功要素1","成功要素2","成功要素3"],"created_at":"","updated_at":""}]}
```
该库仅存在于当前用户环境，各 HR 各自积累；用户要求分享/导出时，输出 JSON 文本或复制文件即可。

## 异常处理

- 用户对某题有选项外的特殊要求（如「职能其实是硬件研发」）：允许用户用一句自由文本补充，Agent 将其并入画像备注，但**默认通道仍是点选**。
- 用户中途要求重选：从该弹窗重新发起 interaction_ask。
- 用户反馈弹窗次数仍多：允许合并交付——先生成默认画像版本，交付后根据用户一句话修正。
